Availability

Status: approved Date: 2026-11-04 Feature: 32 of the suwagcms feature map Needs before it: articles, delete-guard, bot-runtime-sdk
Remaining features Architecture Spec

TL;DR

Anyone can turn an article, a procedure or an action off, from the web, the CLI or the plugin. The list of what uses it is shown first, and being in use never stops it. Turning off changes whether a resource can be found, never whether it exists, so no reference breaks.

Availability is a live setting outside versions. The CMS sends it to one instance of the bot at once, with no push, the others pick it up at their next poll, and it applies to every conversation, also those on an older version. If the bot cannot be reached, the page says the change is saved and not delivered, because “off” is often an emergency and nobody should believe it too early.

Problem

An article is wrong, or a service behind an action is misbehaving, and it has to stop now. The rest of the CMS cannot do that. A push is slow and carries everything else in the working state; deleting is refused while something refers to the resource; and even after a push, a conversation finishes on the version it started on, so the old content keeps being used by the conversations already open.

The bot's other routes accept versions and report them, so nothing else would reach a bot outside a version.

Goals and non-goals

Goals

  • Turn a resource off and on, from any door, with one action.
  • See what uses it before it goes off, without being stopped by it.
  • The change reaches the bot at once, on every version; other instances of the bot pick it up at their next poll.
  • An honest answer about whether the bot has it, as with versions: what the bot reports, not what the CMS tried.

Non-goals optional

  • Facts and knowledge bases: README gives them no availability.
  • Conditions or schedules: on or off only, as README's table of Rasa terms says.
  • Availability inside a file of changes: suwagcms apply changes the working state and this is not part of it.
  • Telling the bot's code which articles to leave out of its search: an item of article-search-feed.
  • Acting on it in a conversation: the bot's engine does, asking the SDK.

Scenarios

1. Marta takes a wrong price list off the air

  1. On the article cennik she flips the switch. A dialog lists what uses it: the article rabaty, through a link in its content. She confirms.

  2. The page says Off, “Bot confirmed”. New searches on the bot leave cennik out. No version was created and nothing was pushed, and the conversations still on v12 get the same answer from the SDK as those on v14.

2. An agent, with the list first

$ suwagcms availability off article cennik Used by: article rabaty, content Nothing changed. Repeat with --yes to turn it off. $ echo $? 1 $ suwagcms availability off article cennik --yes Used by: article rabaty, content Turned off. Bot rzeczoznawca confirmed. $ echo $? 0

3. The bot is down

$ suwagcms availability off article cennik --yes Turned off in the CMS, not delivered: cannot reach http://rzeczoznawca.internal:8080. Check that the bot is running, then send again. The bot still has the previous setting. Send it with: suwagcms availability send $ echo $? 1

4. Two instances behind a load balancer

  1. The change reaches instance A, which writes it to the bot's shared store. Instance B finds it the next time it polls, within seconds, and from then on answers the same on all versions.

Behaviour

What off means

OffEffect
Articleleft out of search; a procedure naming it explicitly still gets it
Procedurethe model cannot start it, even from an article's guide; conversations already in it finish
Actionthe SDK says it is off, and the bot's engine takes the step's onFailure, which makes it a usable emergency switch

The bot's engine carries these out, in its own repository. The SDK gives it the answers, so that bots cannot differ on them, and this spec's criteria check those answers.

How a change travels

Each message holds everything that is off, never a single change, so a missed one repairs itself with the next, and whenever the CMS reads the bot's status (the Versions screen, suwagcms versions status) and the bot reports a lower number, the CMS sends the whole set again, so a bot that was down or restarting catches up without anyone sending. A message the bot did not take is also sent again a minute after each try, until the bot confirms it; then the retries stop, and while nothing is pending the CMS calls no bot. A retry always carries the whole set as it is at that moment with the latest number, so a newer change replaces what was pending instead of queueing behind it. The number goes up with each change, so a slow older message arriving late cannot undo a newer one. The bot reports what it has in its state, and the page shows that, as it does with a version.

Contract

This adds to the public contract between the CMS and any bot. The shapes are published with the bot runtime's JSON schema.

RouteDoesAnswers
PUT /suwagcms/availabilitytakes the number and everything that is off, as kind and id, and for a former id of a renamed resource upToVersion, the last version it counts in; a number lower than the one held changes nothing; safe to repeatthe state
GET /suwagcms/statealso reports what is off and its number, from the store, so every instance gives the same answerthe rest of the state, plus these

A store a bot supplies keeps this setting alongside the versions, and itself keeps the higher number, since the instances sharing it have no lock in common. The bot's code asks IBotDefinitions.IsOff(version, kind, id).

Decisions optional

  • A resource in use can be turned off, with the “used by” list shown first (README), because it cannot break a reference.
  • In the CLI the list comes first by making --yes necessary only for a resource in use: a script stays one flag away, and the emergency path stays one command.
  • A change is saved even when the bot cannot be reached, and exits 1: the intent stands and repairs itself on the next send, while the exit code keeps an agent from taking it for done.
  • Availability is not an edit of the resource and is not part of the working state, so it does not create a reason for a new version, while it shares the same per-bot ordering as saves.
  • conversation cannot be turned off, because the format requires it as the base of every conversation, in the same spirit as the rule that it cannot be deleted.
  • The bot's routes have no key until cms-identity (owner's decision), and this request carries none.
  • An undelivered message is retried every minute until the bot confirms it (owner's decision), so an emergency switch reaches a bot that comes back with nobody watching. What is pending is one due time per bot, never a message, so a newer change replaces it and nothing queues; it lives in the CMS's memory only, and after a restart of the CMS the next change, push, send or read of the bot's status repairs it, because trying every bot at start would also call bots nobody left behind.
  • Reading the bot's status also sends the whole set again when the bot reports a lower number: it already reaches the bot and sees its number. The ask for the declaration does not, because it sits below availability in the server's layers. The time a message last reached the bot is not shown, since no status of the CMS has a place for it.
  • What is off is chosen from the working state, so a resource deleted from it cannot be turned off for conversations on an older version that still hold it: its setting goes with it, and it is on again for those conversations after the next send. An emergency switch stays undeleted and off until no version in use holds it.
  • The setting is kept under the resource's stable uuid, as a row only while it is off, so a rename cannot lose it and no row means on.
  • A change of id is remembered with the latest version at that moment, whether the resource is off or not. A message names a resource that is off under its current id on every version, and under each former id only up to that version, because a new resource may take the old id afterwards.
  • Deleting or renaming a resource that is off changes the set, so its number goes up and the page says the bot does not have it yet; a save itself never calls a bot.
  • If a push cannot deliver the set, it fails and sends no version, because a new version must never run without it. A bot that was never told anything is sent nothing before a push.

Risks and assumptions

“At once” has a limit. Delivery is immediate to one instance; the others take up to one poll, 5 seconds by default. In that window one instance may still run a turned-off action.

A failed delivery leaves the bot as it was during an emergency. The page makes this loud, and the retry repairs it within a minute of the bot coming back, unless the CMS restarted in between.

A bot that can never take the message is called every minute. A bot on an SDK without the route, or one whose store holds a higher number, never confirms, so the retries go on until it is fixed; each is one small request.

A new resource can take the id of a renamed one. A former id counts only up to the last version that can hold it, but a new resource that takes an old id and is turned off also counts for the older versions that hold the renamed resource under that id.

The route has no key. Until cms-identity, anyone who can reach a bot can switch its actions off, or back on. Only a trusted network may reach it.

A bot's own store is now holding a setting as well. A store a bot supplies has to keep it, which changes what such a store must do. Suwagcms.Sdk is not yet published, so no outside store is affected; after publishing it would be a breaking change.

The feature map lists only articles as needed first, but the list of what uses a resource comes from delete-guard, and it belongs to the first cut, so it will exist by then.
