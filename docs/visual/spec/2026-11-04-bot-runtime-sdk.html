SDK in the bot

Status: approved Date: 2026-11-04 Feature: 29 of the suwagcms feature map Needs before it: sdk-validator
Feature map Architecture Spec

TL;DR

A bot adds the Suwagcms.Sdk package and gets routes that accept a version, validate it and load it without a restart, and report which version the bot has. A conversation finishes on the version it started on, because the SDK keeps an old version until its last conversation ends.

A bot may run in several instances: the SDK writes to a store the bot provides, the other instances poll it, and every instance reports the same state. The default file store is for one instance. The routes have no key yet, so until cms-identity they must be reachable only from a trusted network.

Problem

Suwchatbot reads its definition from files once, when it starts, so a change means a restart and all running conversations meet the new procedures at once. README decides otherwise: a bot runs a pushed version, loads it without a restart, reports it, and never changes a procedure under a customer. Every bot would have to solve this itself unless the SDK does; and building it now, in the first cut, tries the version format on a running bot before the package is published and the format gets hard to change.

Goals and non-goals

Goals

  • A bot takes a version with little code of its own, with no restart.
  • A version that fails validation never reaches a conversation, and the bot keeps what it had.
  • A conversation sees one version from beginning to end.
  • Several instances agree on what the bot has.
  • A public contract that a bot outside .NET can implement.

Non-goals optional

  • Running procedures: the bot's engine does that.
  • Telling the CMS what the bot supports: bot-declaration adds its route.
  • Availability: availability. Articles for search: article-search-feed.
  • A key on the routes: the owner decided they stay open on a trusted network until cms-identity.
  • A bot fetching versions by itself, for a bot behind a firewall: added when the first such bot appears.

Scenarios

1. A new version while a conversation is running

  1. A customer's conversation started on v12. The CMS pushes v14. The bot validates it and says it has v14.

  2. A new customer gets v14. The first customer keeps v12 until the end of the conversation.

  3. When the bot's code reports that no open conversation uses v12, the SDK removes it.

2. A bad version

  1. A push brings a document that fails validation. The route answers with every mistake. The bot still has v12, and nothing in its conversations changes.

3. Two instances behind a load balancer

  1. A push reaches instance A, which writes v14 to the bot's shared store. Instance B finds it the next time it polls.

  2. Asked for the state, either instance answers v14, because both answer from the store.

  3. A conversation that started on instance A continues on instance B on the same version, loaded from the store.

4. A restart

  1. The bot restarts and has v14 again, without any push.

Contract

This is the public contract between the CMS and any bot; the version document itself is described in version-create. The shapes of the state answer and of a refusal are published with the format's JSON schema.

RouteDoesAnswers
GET /suwagcms/statesays what the bot has, from the store, so every instance gives the same answerbot id, current version or none, versions held, versions in use, and the reason when the store cannot be read
PUT /suwagcms/currenttakes a number and that version's digest, and makes a held version current (version-rollback); safe to repeatthe state, or a refusal: 409 when it is not held or holds another document, 422 with every mistake when it no longer validates, 503 when the store failed
PUT /suwagcms/versions/{number}takes a version document and its digest; safe to repeatthe state, or a refusal with every mistake

Decisions optional

  • A bot may run in several instances, through a store it provides (owner's decision). The default file store is for one instance, so a one-instance bot needs nothing more.
  • The bot's routes have no key in the first cut (owner's decision): like the CMS they run on a trusted network, and a per-bot key arrives with cms-identity.
  • The bot's own code reports versions in use, because only the bot knows when a conversation is over, and an expiry rule in the SDK would end conversations it knows nothing about.
  • A bot validates a version itself even though the CMS already did: the same library at both ends costs little, and a bot never runs something it has not checked.
  • The “current” version is the last one made current, not the highest number. A version the bot does not hold becomes current by being sent; one it holds needs PUT /suwagcms/current, as sending it again changes nothing.
  • The bot's code reports the versions in use for the whole bot, not per instance: a bot with several instances already keeps its conversations in a shared place and answers in one query, and the SDK needs no way to notice instances that went away.
  • A document with another bot's id is an ordinary refusal, like any other invalid document; the bot gives its id when it sets the SDK up.
  • The version document is one JSON object: formatVersion, bot, number, digest and the lists of the definition. The digest is the SHA-256 (lower-case hex) of the document in canonical form: UTF-8 without white space, object members sorted by name, the digest member left out. Same number and same digest is the same document; an identical document sent again for a version that is not current changes nothing, and PUT /suwagcms/current, specified in version-rollback, is what makes it current.
  • Refusals answer 422 (invalid document), 409 (the number holds another document) or 503 (the store failed), as Problem Details with the mistakes in mistakes.

Acceptance criteria

  • AC-bot-runtime-sdk-1 A test bot built on the packed Suwagcms.Sdk package, with only its setup call, its route call and a store, accepts a version over PUT /suwagcms/versions/{number} without a restart, and reports it on GET /suwagcms/state.
  • AC-bot-runtime-sdk-2 Asked for the current version before any push, the SDK says there is none, and the state route reports none.
  • AC-bot-runtime-sdk-3 A version that fails at the Version stage is refused with every mistake, and the state stays as it was.
  • AC-bot-runtime-sdk-4 A document with another bot's id, an unknown formatVersion, or a digest that does not match is refused, naming the reason, and the state stays as it was.
  • AC-bot-runtime-sdk-5 After a new version is accepted, the SDK gives its number as current, and the definition of an earlier number is still available.
  • AC-bot-runtime-sdk-6 Sending the same number and document twice succeeds and changes nothing; the same number with another document is refused.
  • AC-bot-runtime-sdk-7 A lower number than the current one that the bot does not hold is accepted and becomes current.
  • AC-bot-runtime-sdk-8 A version neither current nor reported as in use is removed; one reported as in use is kept; the current one is never removed, even if reported as unused.
  • AC-bot-runtime-sdk-9 When the bot's code has never reported what is in use, no version is removed.
  • AC-bot-runtime-sdk-10 After a restart, a bot with the default file store reports the same version and can give the definition of any version it held.
  • AC-bot-runtime-sdk-11 With two instances sharing one store, a version pushed to one becomes current on the other at its next poll, and GET /suwagcms/state gives the same answer on both.
  • AC-bot-runtime-sdk-12 The definition of a version held in the shared store is available on every instance, whichever one took it.
  • AC-bot-runtime-sdk-13 When the store fails during a write, the route answers with the reason and the state stays what it was.
  • AC-bot-runtime-sdk-14 When the store cannot be read while polling, the instance keeps serving what it has, and the state route says the store cannot be read.
  • AC-bot-runtime-sdk-15 The default file store and a store supplied by a test give the same state for the same scenario.
  • AC-bot-runtime-sdk-16 The published schema of every bot route (the state answer, a refusal, PUT /suwagcms/current, the declaration, the availability message and the test route) is compared on the gate, so a change without its schema fails with the command that regenerates it.

Risks and assumptions

The routes have no key. Anyone who can reach the bot can replace its definition, so until cms-identity the /suwagcms/* routes must be reachable only from a trusted network. The check of the bot id stops a mistake, not an attacker. The SDK's documentation has to say this plainly.

Old versions may never end. An abandoned conversation holds its version for as long as the bot's code keeps reporting it. The bot decides when a conversation expires; version-push shows the versions still in use, so the build-up can be seen.

The format soon becomes public. The first criterion tries the contract through the packed package before the owner publishes it to nuget.org; a change of meaning later needs a new formatVersion.

The CMS has to reach the bot. A bot behind a firewall with no way in cannot take a push. When the first such bot appears, the SDK gets a way to fetch versions, and the rest of the model stays.

Reports of versions in use are assumed to cover all of a bot's instances, for example from its shared conversation store. A per-instance report would let one instance remove a version another still needs.
