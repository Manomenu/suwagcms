Procedure editor

Status: approved Date: 2026-11-06 Branch: feature/procedure-editor Feature: 15 and 20 of the suwagcms feature map Needs before it: procedure-model, articles, bot-declaration
Remaining features Architecture Spec

TL;DR

A procedure is edited on a page read top to bottom, like a document, instead of on a canvas of nodes. The page is the shared edit screen every other resource has. Steps are a numbered list; an If holds indented lists of its own. The stored format stays a graph, built on save, so the bot does not change for this part.

An instruction's context becomes knowledge: a list of entries, one per knowledge base. That breaks the published format, so it needs format 2 and a new SDK release. It is incompatible, with no migration and no reader of the old key, and the bot moves in the same change.

A list alone cannot show a loop or a jump, so a Next: row names any step, and an End row closes a branch. Every graph the format allows can therefore be shown, and the SDK gains no rule on a graph's shape.

Problem

Today's creator draws quoteRequest as six nodes on a canvas. To read what the procedure does, an author follows edges across the screen, clicks a node to see its form in a side panel, and looks for mistakes in a separate list. The picture needs its own table, routes, a CLI command and an Arrange button just to remember where a node sits, none of which means anything to a bot. The screen is also the one edit screen that does not share the frame of the others, so Delete and History sit elsewhere on it.

An instruction's context holds articles from any base and searchQueries with no target. A bot has several knowledge bases, and a query cannot say which one it is for. The first bot carries context and never reads it.

Goals and non-goals

Goals

  • Read a procedure from top to bottom and know what it does.
  • The same frame as every other resource: Delete and History in their usual place.
  • Every graph the format allows opens as one list, and saving unchanged changes nothing.
  • See each mistake beside the step it concerns.
  • A query names the base it searches, and a bot says whether it reads knowledge.

Non-goals optional

  • A bot reading knowledge: the later feature knowledge-answers. Here it is stored, checked and delivered.
  • Changing the stored graph: firstStep and next stay.
  • Conditions a model judges: an If chooses a fact and a condition, deterministically.
  • The canvas kept as a second view.
  • Any migration or reader of context: it is removed outright.
  • Undo history, comments on steps, several people editing at once, a phone layout.
  • Creating a global fact from the page: facts have their own screen.

Scenarios

1. Marta adds a step to quoteRequest

  1. She opens quoteRequest and sees the page above. She never sees a next.

  2. Under askContact she clicks + Add step and picks Say. The new row is named say, and she edits the name on the row to thanks. She moves it above whatHappensNext.

  3. She saves. suwagcms procedures show quoteRequest prints askContact → thanks → whatHappensNext. All other steps keep their names and targets, so inform:quoteRequest.whatHappensNext.quoteTime still names the same point in a trace.

2. She adds an If

  1. Below an Ask row she clicks + Add step and picks If. She chooses property.type, then oneOf, then land from the fact's values. An empty Else comes with it.

  2. The Else has no steps and nothing follows the If, so beside the Else she reads: A branch of step 'askProperty' goes to no step. Add a step to this branch, or a Next: row. She adds a row below the If and the mistake goes, without saving.

3. An agent saves a jump

  1. An agent saves a graph where askAge's branch skips straight to whatHappensNext. The save is accepted, because the format allows it.

  2. Marta opens it. In that branch she reads a row Next: whatHappensNext. She renames whatHappensNext, and the row follows. She deletes the step, and the row stays with a mistake beside it.

4. A bot that reads knowledge

  1. Its declaration says knowledge: true. On a Tell row Marta opens Knowledge, picks the base reports, and sees only that base's articles. She ticks reportContents and writes a query. The base is no longer offered for a second entry.

  2. On the first bot, which does not declare it, no such section exists on the page.

A step's next is implicit: it is whatever comes next on the page.

An If is the rules of the step above it

The format has no If step: rules are the next of a step. So an If always hangs on the step directly above it, and that decides where one can stand.

  • An If needs a step directly above it. + Add step is the only way to add one, so it goes below the last step of a list; it is not offered as the first row of a list, or right after another If. A step moves with the If below it by the arrows, which is how an If reaches the middle of a list, and deleting a step with an If below it is refused with that reason, and nothing changes.
  • A branch's conditions are on the row of an If or an Else if, which folds like a step's row: folded, it reads as a line of text such as property.area is at least 500; clicked, it unfolds to the editor. Each row folds on its own, whichever step is selected, and the address keeps which are open, as it does the selected step. A new If, and any row with no condition, is open and cannot fold, so a condition can always be set; clicking a mistake beside a row opens it. Each condition is a fact, global or local, and a condition (oneOf, range, known), fitted to the fact's type. + and adds another, and all must hold, as when does today. There is never free text.
  • Several rules may go to one step: conditions in one rule combine with AND only, so two rules on different facts are how the format writes OR. Both branches show no steps and go on to that step, or one holds the step and the other a Next: row.
  • Else comes with a new If and cannot be removed. + Else if adds a branch before it. ↑ ↓ on the If row move the whole block onto the neighbouring step, since its rules live on that step's next: the steps in the branches stay in them and the list keeps its order; they are disabled with no step on that side or a neighbour with an If of its own. ↑ ↓ on an Else if row swap it with the neighbouring branch, because order decides which condition wins, so swapping with the first makes it the If; the Else stays last, with no arrows. A move that breaks a fact's use is not blocked: the mistake beside the row reports it. The ✕ on the If row (named Remove this If) removes the whole If, asking first when it holds rows; the ✕ on an Else if row (Remove this Else if) removes only it. Every row of the list, a step, an If, an Else if, an Else, a Next:, an End, On failure, On success and a row under Not connected, is one shared row: its tag, its name or editable content, its text, which is the fold toggle where the row folds, then ↑ ↓ where it moves and ✕ where it can be removed, each always in the same place; a control a kind of row lacks leaves its place empty, so the rows line up. + Add step is a menu whose label is never an option to pick, and it comes back to its label after each choice. The rules' order is the branches' order.

How the graph becomes the list

When a procedure opens, one canonical list is rebuilt from the graph, so a graph always looks the same. The order of steps in a file never matters.

  1. Start at firstStep. A step becomes a row of the current list the first time it is reached.

  2. A fixed next to a step not placed yet gives the row below. A next to where the list goes on anyway gives nothing. Any other next, forward or back, gives a Next: row, which ends that list. A step whose next is not the following row shows that row.

  3. No next gives an End row when a row would otherwise follow, and nothing when none would.

  4. Rules give an If, in the order stored, and an action's onFailure gives its two branches. The block's continuation is the first step, in reading order, that two or more branches lead to without going back. With none, the block ends its list.

  5. Each branch is the list from its to up to the continuation, and is empty when to is the continuation. The outer list goes on at the continuation.

  6. Steps no path reaches, or all steps when there is no firstStep, go under Not connected by name, with their mistakes.

Round trip. For every graph the format allows, rebuilding the list and building the graph gives the same firstStep, the same next and rules in the same order, and the same onFailure, with one normal form: a list of rules holding only a default is written as a fixed next, which means the same. Open and Save with no edit sends nothing, because an unchanged page is not dirty, so the revision stays.

Every graph can be shown

The SDK gains no rule on a graph's shape. The existing loop rules stay, and so do the rules on steps that do not exist and on steps no path reaches.

Next: and End

+ Add step also offers Next:, at the end of any list, with every named step of the procedure, forward or back, itself included. It ends that list. Inside a branch it also offers End when a row would otherwise follow. Rows after an If stay possible whatever its branches do: a branch ending in Next: or End simply does not go on to them.

A Next: target follows a rename. A target that no longer exists is a mistake beside the row, stating the fix, and refuses a save until it is fixed.

Step names

The bot, the points inform:<procedure>.<step>.<point> and traces all rely on a step's name, so a name never depends on where its row stands.

  • Every row shows its name, right after its number, and it is edited there: Next: and the points name it.
  • A new row gets a unique name from its block, as today (say, say2). The author can change it: every place that points at it follows, Next: rows included, and a taken name changes nothing. The form says that traces then use the new name.
  • Moving, reordering, or editing what a row holds never changes a name. A deleted row's name is free again.

Mistakes beside their place

After any change, without saving, the page asks the server what the current list would produce, as a dry run. It holds no copy of the rules. Each mistake shows beside its place, says whether it refuses a save or stops a version, and gives its fix. A count at the top of the form lists them, and clicking one shows and selects its place.

On every instruction, inform and whenStalled alike, knowledge replaces context. The rest of the procedure's format is unchanged.

The rule on an article's base judges the result of a save, so moving an article to another base is refused while an entry names it under the old one. An article's own rule is unchanged. Both stages hold in the validator offline. A save with several bad names lists each at once.

  • + Add knowledge offers the bases this instruction does not use yet. Picking one shows only its articles, by title, and its queries.
  • Changing an entry's base clears its articles and keeps its queries, in front of the author.
  • A bot with no bases: the section says so, with a link to the Knowledge screen.
  • A stored article stays listed and ticked even when the form would not offer it, and its mistake shows beside it.

Contract optional

The contract is suwagcms-bot, with the schemas definition-format.schema.json and bot-runtime.schema.json. Its compatibility rule says a renamed field is a new format version, so this is one. What a procedure definition can hold lives in two repositories, so both change. There are no customers, and the owner accepts the removal below.

WhatRule
Format version2. A reader refuses any other with format.version, as today
SDKThe new format comes with a new SDK release, which the owner makes from master with just sdk-publish. 0.1.0 stays on nuget.org, since a release cannot be deleted, and it reads format 1 only
Resources already holding contextNothing converts them. The key is unknown to the new reader, so it is ignored: no rule checks it, no article is protected by it, a version does not carry it, and the next save of that procedure removes it. The words are gone
Frozen versions holding itA version is never changed, so a format-1 version keeps its bytes and digest and can still be listed and compared. It can no longer be pushed or rolled back to: that is refused with format.version. Create a new version from the working state instead
Versions a bot holdsA held version is not validated at a restart, so conversations pinned to an older one finish on it, with its context skipped as an unknown member. Making one current again is refused
Files and batchesA file or batch with context is refused as any unknown key is
SuwchatbotIt moves to format 2 in the same change, in its own repository: its mapping no longer reads context, and it does not declare knowledge, so a version it takes holds none. Its seed needs no change. Reading knowledge arrives with knowledge-answers

Decisions optional

  • One page holds the editor and the knowledge format, because the owner reads them as one piece of work. By ownership they could be two specs, and if they ever part, each criterion goes with its text under its id.
  • This is the procedure-creator spec edited in place, because it is the same feature with a new shape. Its file name and the prefix of its ids stay, since an id is never renumbered. The word in every text becomes editor.
  • Next: replaces a row limited to going back, in the format's own word: every graph can then be shown, so the editor has no second way to view a procedure and the SDK has no rule on shape.
  • End is editor-only: the format already writes an end as a step with no next, so no node is added.
  • Two rules may go to one step: conditions in one rule combine with AND only, so this is the format's only OR across facts, and refusing it would leave no way to write one.
  • context is removed outright: no customers, and a conversion would have to guess a base for each query. A version holding knowledge for a bot that does not declare it is refused at Version, as an undeclared block is.
  • The tags use the writer's words, Ask and Tell, and the format keeps collect and inform: a row's form names both.
  • A declaration field rather than a block: knowledge is a part of an instruction, and it has no row to leave out. It replaces the earlier decision to declare nothing until a second bot showed the need, because the section must hide.
  • With nothing declared the section shows, as blocks do, because nothing is being checked either way.
  • Left out, because no real need shows yet: a query form that tries the query, and a criterion that the layout routes are gone, since deleted tests and EveryRouteHasACommand already leave nothing to guard.

Risks and assumptions

A tangled graph reads as many Next: rows. Nothing refuses it, so a list is only as readable as its graph. The editor always builds what the author arranged, so this comes only from a file.

Dropping procedure_layout is a data migration, on the always-careful list, so a person reads that part of the diff. Node positions are lost, and they mean nothing without the canvas.

Format 2 stops version creation for a bot still on an older SDK, with declaration.formatVersion naming both, until it moves. The SDK must be released before the bot's package reference can follow it.
