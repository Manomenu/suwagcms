Spec

HTTP actions

Status: approved Date: 2026-11-04 Feature: 22 of the suwagcms feature map Needs before it: bot-profiles, sdk-validator
Feature map Architecture Spec

TL;DR

An author defines an action in the CMS: a description, typed parameters and results, and an HTTP call with a URL, a method and references to secrets. It is saved like any other resource, through the web, the CLI and the plugin.

The CMS only holds the definition. The bot makes the call, with secret values from its own environment, and the SDK gives every .NET bot the same meaning of “run this action”: what is sent, what comes back and what counts as a failure. An action never names a fact.

20criteria

Problem

A procedure often needs something only another system knows, such as whether an address is served. Without actions in the CMS, each such call is code in the bot, with a deployment for each change, and nothing a procedure's author can see or check.

The tempting shortcuts each cost something later. An action that writes facts itself can serve one procedure only, and the CMS cannot check it, which is what README leaves out of Rasa. A secret typed into a definition travels into every version, export and diff.

Goals and non-goals

Goals

  • Define, read, change and delete an action from any door, with the same refusals.
  • A contract of typed parameters and results that says nothing about facts, so one action serves many procedures.
  • No secret value in the CMS, in a version or in any output.
  • One meaning of an HTTP action, published and tried by tests, so two bots cannot read it differently.

Non-goals optional

  • Using an action in a procedure: action-block.
  • Actions written in the bot's code: code-actions.
  • Trying an action from the CMS: action-test-run.
  • Turning an action off: availability.
  • Retries, OAuth flows, request body templates, and a call that is not HTTP: nothing needs them yet, and a service that needs them can sit behind a code action.

Scenarios

1. An agent adds an action

$ suwagcms actions add --file checkServiceability.yaml Saved checkServiceability, revision 1.

2. A secret typed in by mistake

$ suwagcms actions edit checkServiceability --file checkServiceability.yaml Refused, 1 mistake: action.secret.literal Header 'Authorization' holds a literal value, and the CMS never stores secrets. Write 'Bearer {secret:CRM_TOKEN}' and set CRM_TOKEN in the bot's environment. $ echo $? 1

3. A bot runs it

  1. The bot's engine asks the SDK to run checkServiceability with the address Polna 3, Suwałki.

  2. The SDK posts the address as JSON, with the token from the bot's environment in the header. The service answers { "serviceable": "yes" }, and the SDK returns the result serviceable = yes. What that does to a fact is up to the procedure's step.

4. The service is down

  1. The service answers 503. The SDK returns a failure with the reason, and no results. The token appears nowhere in the reason.

Behaviour

A save behaves as the “How every save behaves” section of the global-facts spec describes: all mistakes at once, unknown fields refused, a dry run, and revisions. Like a fact, and unlike a procedure, an action has no unfinished state: it is whole or it is refused. As with a procedure, the CLI takes one whole action from a file, in YAML or JSON.

What a save checks

FieldRule

descriptionrequired, also on each parameter and result
parameters, resultsoptional; each has a camelCase name and a type with its constraints, by the same rules as facts: enum with values, int with min and max, text with maxLength
methodGET, POST, PUT, PATCH or DELETE
urlan absolute http or https address with no user or password; each {name} in it is a parameter of this action
headersoptional; literal text, and {secret:NAME} where a secret goes
a secret's namecapital letters, digits and underscores, starting with a letter
timeoutSecondsoptional, 1 to 60, 10 by default

Keeping secrets out

The CMS cannot tell a secret from text in general, so it refuses the places a secret usually lands:

WrittenResult
literal text in a header whose name is Authorization, Proxy-Authorization or Cookie, or contains key, token, secret, password or authrefused; a value there has to hold a {secret:…} reference
a query parameter in the URL with such a name and a literal valuerefused, with the fix to send it in a header or behind a code action
{secret:…} in the URLrefused: URLs end up in logs

What running an action means

This is part of the public contract with bots. The SDK does it for a .NET bot, and a bot outside .NET does the same. The bot's engine decides when to run an action; the SDK takes the action, the parameter values, and a way to find a secret, and returns results or a failure.

StepMeaning
parameters in the URLa {name} is replaced by the value, URL-encoded
the other parametersGET and DELETE send them as a query string; the others as one JSON object
resultseach is the member of that name at the top level of the JSON object in the answer
no results declaredany 2xx answer is a success, and its body is ignored

What counts as a failure

A failure has a reason and no results, so a half-understood answer is never used. There are no retries, since a repeated POST may do the work twice.

SituationReason says
a parameter is missing or does not fit its typewhich parameter, and what fits; nothing is sent
a secret cannot be foundits name; nothing is sent
no connection, or no answer within the timeoutwhich, and the time limit
an answer outside 2xx, redirects includedthe status
results are declared and the answer is not a JSON object, one is missing, or one does not fit its typewhich result, and what fits

Format

Part of the public contract with bots. YAML as the CLI reads and prints it; on the wire it is the same structure in JSON.

Decisions optional

  • The bot runs actions, not the CMS (README), so saving, showing or versioning an action never calls its URL.
  • The SDK runs an HTTP action rather than leaving that to each bot's engine: the definition is a public format, and without one runner two bots could send the same action differently. The engine still decides when to run it and what to do next.
  • Results come only from the top level of the answer, which keeps the format small; as decided below.
  • Secrets go in headers only, because URLs end up in logs; a service that wants a secret in its URL sits behind a code action.
  • Any answer outside 2xx is a failure, with no status mapping per action, as ElevenLabs' tool node routes on success or failure only.
  • Parameter and result descriptions are required, like those of facts, because a later reader of a mapping has nothing else to go on.
  • A result comes only from the top level of the answer: a nested service sits behind a code action, and an optional field can be added later without a new format version.
  • A definition reaches only variables with a prefix: CRM_TOKEN reads SUWAGCMS_SECRET_CRM_TOKEN, and a bot may supply its own way to find a secret, so the bot's owner chooses what the CMS can name.

Acceptance criteria

  • AC-http-actions-1 An action with parameters, results, headers and a timeout saved in the web or with suwagcms actions add --file reads back as written, in the web and with suwagcms actions list and show, in YAML and JSON.
  • AC-http-actions-2 An action with only an id, a description and an implementation is saved.
  • AC-http-actions-3 The output of suwagcms actions show is accepted back by suwagcms actions edit --file without a change of meaning, in both formats.
  • AC-http-actions-4 A blank description of an action, parameter or result, an id or name that is not camelCase, an id the bot's actions already have, a missing implementation and a type breaking the rules of facts are reported at once, each with its fix, and nothing is saved.
  • AC-http-actions-5 A method outside the list, a URL that is not absolute http or https, a URL with a user or password, a {name} that is not a parameter and a timeout outside 1 to 60 are each refused with a fix.
  • AC-http-actions-6 A malformed secret name, {secret:…} in a URL, a literal value in a header with a sensitive name, and a literal value in a query parameter with a sensitive name are each refused with a fix showing the reference to write.
  • AC-http-actions-7 A saved action holds its secrets only as names, in the web, in show, in --json and in the API's answers.
  • AC-http-actions-8 The same bad action is refused with the same codes and messages by the web, the CLI and the validator offline, and the web shows each beside the field its path names.
  • AC-http-actions-9 --dry-run on an add, edit or delete gives the same answer and changes nothing; an edit or delete based on an old revision is refused with the current one; a field the API does not know is refused, naming it.
  • AC-http-actions-10 An action of one bot is not listed for another, and two bots can each have an action with the same id.
  • AC-http-actions-11 An unused action can be deleted in the web and with suwagcms actions delete, and is gone from both.
  • AC-http-actions-12 While an action is added, edited, shown or deleted, the CMS sends no request to its URL.
  • AC-http-actions-13 Run by the SDK against a test service, an action sends its method and headers, fills URL parameters URL-encoded, and sends the other parameters as a query string for GET and DELETE and as one JSON object otherwise.
  • AC-http-actions-14 Run by the SDK, a {secret:NAME} reaches the test service as the value found for that name.
  • AC-http-actions-15 Run by the SDK, a 2xx answer returns each declared result by name; with no results declared, any 2xx answer is a success whatever its body.
  • AC-http-actions-16 Run by the SDK, each situation in “What counts as a failure” returns a failure with its reason and no results, sends at most one request, and sends none when a parameter does not fit or a secret is missing.
  • AC-http-actions-17 An action's own timeout, or 10 seconds without one, ends a call to a test service that does not answer, as a failure saying so.
  • AC-http-actions-18 No reason returned by a run holds a secret's value, even when the test service repeats it in its answer.
  • AC-http-actions-19 Each suwagcms actions command has its line in the plugin's main skill, which gives the file format and says a secret is written as a reference.
  • AC-http-actions-20 The view of an action shows the procedures that use it.

Risks and assumptions

Whoever can edit an action can send a bot's secret to any address. A definition names the URL and the secret, and the bot obeys, with no identity in the CMS yet. README accepts a trusted network until cms-identity; the prefix decided above narrows what a definition can reach, and a version only reaches a bot through a push.

Refusing by header name is a net with holes. A secret in a header called X-Customer, or in the URL's path, gets through. The check catches the usual mistake, and the form's hint and the plugin's skill say the rest.

A bot outside .NET implements this contract itself and could read it differently. Its tests are its own, tied to the format's version.
