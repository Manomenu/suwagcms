Spec

Pushing a version

Status: approved Date: 2026-11-04 Feature: 30 of the suwagcms feature map Needs before it: version-create, bot-runtime-sdk
Feature map Architecture Spec

TL;DR

A bot's page says Bot has: v12, Latest: v14 and offers Push v14. The number shown is the one the bot reports, not the last one the CMS tried to send, so a failed push shows as failed and the bot keeps what it had.

People and agents may both push, through the web, the CLI and the plugin. With this feature, the first cut is complete: facts, articles and procedures reach a running bot.

Problem

After version-create, a frozen version sits in the CMS with no way to reach a bot. A CMS that shows what it last sent will sooner or later lie: the push may have failed, or the bot may have restored something else. Anyone deciding whether a fix is live needs the bot's own answer.

Goals and non-goals

Goals

  • See which version a bot has, as the bot reports it, and whether anything newer exists.
  • Push the latest version with one action, from any door.
  • A failed push is visible and leaves the bot as it was.
  • A slow bot never holds up anyone's editing.

Non-goals optional

  • Choosing another version and rolling back: version-rollback owns the version select and --version.
  • Sending availability changes: availability.
  • Retrying by itself: a person or an agent decides, and a repeated push is safe.
  • A key on the bot's routes, and recording who pushed: they arrive with cms-identity and change-history.

Scenarios

1. Marta pushes the latest version

  1. The page says Bot has: v12, Latest: v14. She presses Push v14.

  2. The bot answers that it has v14, and the page says Bot has: v14, up to date.

2. An agent pushes

$ suwagcms versions create Created v14 sha256 3f9a…c21e $ suwagcms push Bot rzeczoznawca has v14. $ echo $? 0

3. The bot is down

$ suwagcms push Push of v14 failed: cannot reach http://rzeczoznawca.internal:8080. The bot last reported v12, at 21:40. Check that the bot is running and that the CMS can reach it, then push again. $ echo $? 1

4. The bot refuses

  1. The bot's own validation rejects the version. The page shows the push as failed with the bot's mistakes, and still says Bot has: v12.

5. Marta keeps editing during a slow push

  1. A push waits on a slow bot. An agent saves an article of the same bot at that moment, and the save goes straight through.

Behaviour

Which version the page shows

When the page opens, and with suwagcms versions status, the CMS asks the bot. A bot in several instances answers the same from any of them. The answer also lists the versions the bot still holds for conversations in progress, so a build-up of old versions can be seen.

Decisions optional

  • The version shown is the one the bot reports (README), so the page never claims more than the bot does.
  • A push makes no attempt of its own to retry: repeating is safe and simple, and a quiet retry would hide a sick bot.
  • No save waits for a push, because a slow bot must never queue up edits of its own definition.
  • The bot's routes have no key in the first cut (owner's decision), so the request carries none.
  • A push waits 30 seconds for a bot, a server setting (accepted assumption: long enough for a bot to validate a whole version; a repeat is safe if a slow bot was still working). Asking a bot for its state waits 5 seconds, because a person waits on the page.
  • A push counts as done only when the bot's answer names that version as current: a 200 alone proves nothing, since sending a document the bot already holds changes nothing. A version the bot holds that is not current is not made current by a push; that is version-rollback's route.
  • Neither a lock nor a transaction is held while the bot is called: the CMS reads what it needs, lets go, calls the bot, and then records the attempt.

Acceptance criteria

  • AC-version-push-1 In the web and with suwagcms push, pushing the latest version to a running test bot makes the bot hold it, and the page and suwagcms versions status then show that number.
  • AC-version-push-2 The version shown comes from the bot's answer: when the bot has been given another version directly, the page shows that one, not the last one the CMS sent.
  • AC-version-push-3 The page offers a push of the latest version when the bot has an older version or none, and offers none when it is up to date or the CMS has no version.
  • AC-version-push-4 With the bot unreachable, the page says so with the last reported number and its time, and a push fails with that reason and exit code 1.
  • AC-version-push-5 A bot that does not answer within the time limit fails the push with a reason saying so, and the bot's shown version stays as it was.
  • AC-version-push-6 When the bot refuses a version, the push is shown as failed with the bot's mistakes, the shown version stays as it was, and the CLI exits 1.
  • AC-version-push-7 A bot in two instances that share a store, pushed through one, shows the new version when the CMS asks either of them.
  • AC-version-push-8 A bot whose answer names another bot's id is shown as a wrong address, naming it.
  • AC-version-push-9 A push changes neither the working state nor any version.
  • AC-version-push-10 suwagcms push when the bot has the latest version says so, sends nothing and exits 0; with no version it exits 1 and says to create one.
  • AC-version-push-11 A save of the same bot during a push waiting on a slow bot completes without waiting for it.
  • AC-version-push-12 Every attempt is recorded with its time, version, result and reason, and the page and suwagcms versions status list the recent ones.
  • AC-version-push-13 The page and suwagcms versions status list the versions the bot still holds for conversations in use.
  • AC-version-push-14 suwagcms push asks for no confirmation, and with --json returns the result, the reason and the version the bot reports.
  • AC-version-push-16 From a real server and a test bot, through the CLI: a fact, a base, two linked articles and the procedures are created, deleting a used article and closing a loop are refused, a version is created and pushed, and the CMS shows what the bot reports; with the bot stopped, a push fails visibly, and after its return the bot still reports the earlier version.
  • AC-version-push-17 A version, also an older one, holding a block the bot does not declare now is refused, naming the block, and nothing goes to the bot; a bot with no declaration or a wrong answer goes on to its own validation.

Risks and assumptions

The bot's routes have no key. Anyone who can reach a bot can push to it directly, and the page would faithfully show the result. Until cms-identity, both the CMS and the bots' routes run only inside a trusted network.

The CMS has to reach the bot. A bot behind a firewall with no way in shows as unreachable, and a push fails. When the first such bot appears, it gets a way to fetch versions by itself.

Old versions can pile up in a bot. The page lists the versions still in use, so this shows; ending an abandoned conversation stays the bot's decision.
